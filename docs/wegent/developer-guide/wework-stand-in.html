Wework Stand-in

The primary profile has one Stand-in instructions field for responsibilities, background and preferences shared with scenario roles. Existing two-field content is consolidated without loss on save. Connections initially shows connected objects with their scope and handling summary; Add connection opens project or DingTalk selection. Scope, exclusions, tags and handling policies live in the connection editor. Device, working directory and model remain visible in Execution environment. Switching devices loads that Executor’s independent profile and is blocked while edits are unsaved. Directory and model defaults apply to new work; existing conversations retain their environment. The Issue composer has no separate stand-in toggle; receive scopes are managed in My stand-in.

The Chinese UI calls this feature “分身” (My Stand-in: “我的分身”); English labels and internal stand-in identifiers remain unchanged. Stand-ins belong to the person. The collaboration navigation lists existing personal stand-ins by name, enablement and connected projects, even before their first execution. Clicking a stand-in opens its settings. Unnamed stand-ins use Default stand-in with an index when needed; connected project names never become implicit stand-in names. Actual execution history appears below, grouped by project. History rows open their Runtime tasks. Configuration is a secondary Settings page. The Settings drawer edits the selected stand-in and its name directly, without another stand-in picker. The UI consistently calls them stand-ins; the stored roles array is their configuration list, not another user-facing role layer.

The project toolbar opens Project stand-in. It selects an already connected stand-in first, otherwise the first eligible personal stand-in. Existing instructions, agent and automatic-handling status are shown read-only. For an enabled project, the primary action is exclusively Disable for this project. Saving disconnects every matching stand-in from this project, using exclusions for all-project sources and disabling the collaboration source of project-bound agents. Global enablement, other projects and existing executions remain unchanged. For a disabled project, the primary action is exclusively Enable and use for this project, enabling the selected stand-in and connecting the project. The UI explains that enablement also applies to its other connected projects and only new assignments after enablement are handled. Agent selection and instructions remain unchanged. A separate link explicitly opens personal settings and explains their cross-project effect. Save or Cancel returns to the original project, preserving an explicitly saved execution device. A first connection enables only the current project rather than all projects.

Create a stand-in for this project creates a personally owned stand-in with the project name and a single-project connection, also visible in personal settings. Instructions are expanded; execution settings are collapsed. Secondary views stay scoped to the selected stand-in without another picker. Choosing a project agent connects its owning project and limits the stand-in to it. While signed out, no cloud personal-agent catalog is requested and no login or load-failure hint is shown; the general assistant and eligible project agents remain available. Genuine catalog failures retain an explicit retry action.

Instructions reuse the normal composer, skills, plugins and Goal mode. Device, model and code workspace live under More settings. Saving does not depend on cloud catalogs, project device bindings or model readiness; dispatch validates the current actor, Issue permission and the agent's device and model policies.

Every edit, including the automatic handling toggle, takes effect only after Save. Prompt and execution changes merge into the current role through functional updates, so delayed composer callbacks cannot overwrite newer toggle, device or workspace values. Failed saves retain the draft; version conflicts cannot overwrite another editor. Clicking the drawer backdrop, closing, or pressing Escape requests dismissal. Unsaved changes open a centered confirmation dialog; Keep editing preserves the draft and drawer, while Discard closes it. Back from a secondary page discards that page's edits. Disabling stops new assignments while existing Runtime tasks continue.

A role can cover all participating collaboration projects, including future projects, with individual exclusions, or a selected project list. Optional tags narrow its scope. Settings are account-scoped in the selected Executor's SQLite database; devices remain independent. Settings belong to the Executor that stores them. After a desktop device identity change, reads and scheduling bind the document and its stand-ins to the current Executor, preserving instructions, scopes, versions and assignment cutoffs. Saves still reject settings addressed to another device. The frontend passes the selected Executor explicitly as the request target, without deriving routing from stored device fields, duplicating local-device or project-access validation, or rewriting device ownership in responses. The Executor validates ownership and permissions. Local projects are displayed only on their owning device.

One personal document owns stand-in configurations and versions. Legacy project configurations migrate transactionally into roles preserving project scopes, assignment cutoffs and original project-agent authority. Project-addressed RPCs are projections over this document, with no duplicate project persistence.

Model catalog and execution references​

Stand-ins and ordinary tasks share the model picker, classification, sorting, and option rules. Cloud models use their original UnifiedModel catalog objects directly, without a round trip through execution models or changes to catalog names, labels, or config.ui. Native Executor catalogs require only one display adaptation and reuse the common Codex catalog helpers for provider metadata.

Display models and RunnerModelIdentity are stored separately. Display models serve the UI; execution references contain only the actual runtime, provider, model ID, and the cloud resource name, type, namespace, and owner. Saving submits only the execution reference, not model configurations or credentials. The public resource type means a public resource, not a public-network endpoint. Intranet, public-network, and overseas labels come from the original catalog; unmarked models are not automatically labeled public-network.

Desktop and mobile use the same complete model identity comparison, distinguishing same-name providers, namespaces, and owners. Option identifiers are independent of display names and preserve existing identifiers. Changing the device or runtime invalidates old catalog requests; unavailable saved models retain the recovery entry.

The existing CI stand-in-profile checkpoint group includes the original stand-in-profile-settings scenario and the new stand-in-model-catalog scenario. The latter compares ordinary and stand-in labels for real Backend intranet, public-network, and unmarked models sharing an upstream model ID, then validates persisted execution references. The runner and CI catalog validator share checkpoint-group expansion so registered scenarios cannot be left outside CI.

Multiple stand-ins handling work​

Each enabled stand-in independently checks its connected sources, tags, handling policy, and enable-time cutoff. Every eligible stand-in handles the work. Tagged matches do not suppress unrestricted stand-ins. Scheduling, priority ordering, and AI role selection have been removed; matching does not invoke a model.

Project tasks have independent Runtime executions and bindings for each assignment and stand-in. Repeated notifications and polls reuse each identity's existing execution, including failed or archived work. Existing executions are identified by assignment, account, project, and stand-in provenance, so task naming changes do not replay work. Assignments already bound before the upgrade are not dispatched again. Preparation failure for one stand-in is reported while the others are still attempted.

DingTalk collection runs on a 15-second interval. Connections to the same group or contact on the same account share one source query, then each enabled connected stand-in receives the messages. Distinct sources are queried sequentially with independent pagination, at most 100 messages per request; remaining pages are read on later rounds. Collection time can increase actual latency. Deduplication includes the account, stand-in, and source, so repeated messages do not replay and another stand-in's records do not suppress intake. Private chats currently require individual contact connections; there is no all-private-chats option. Failed associations are atomically persisted per stand-in as ungrouped work with the error, awaiting manual confirmation without repeated model calls or blocking shared pagination and other identities. Associating messages with existing work can still use a model, independently of the removed role selection.

Cloud projects reuse assignment notifications already received by Wework instead of scanning projects or polling assignments every five seconds. The desktop notification entry uses the loaded inbox and online device list, deduplicates by account, device and notification, and calls the existing Runtime RPC on each relevant device. Each device checks enabled personal settings, the current user, project, assignment identity and tags before validating assignment status and the enable-time cutoff. Each dispatch reads assignments only once. Local projects retain scheduling against local storage without cloud project or assignment requests. Historical, unrelated, unassigned and already-bound work is excluded before ordinary task creation, binding, sessions and result views are reused. Reloading the desktop reprocesses the loaded inbox while existing Runtime tasks are reused without another assignments request or execution. Automatic handling requires receipt of an assignment notification; failures are logged instead of retrying on every inbox refresh. Before task creation, the original notification still offers Delegate for explicit manual recovery; an existing failed task retains Retry. Explicit settings saves reconsider loaded notifications for the updated device. Manual delegation works with automatic handling disabled, using the explicitly chosen stand-in or the first stand-in connected to the project when none is specified; no available connection returns an explicit error. Execution provenance records the owning stand-in. Cloud execution retains current Issue permission checks; local work remains functional offline. No new backend queue or distributed lock is introduced.

Feedback in collaboration notifications​

Stand-in handling has no Issue board-status or completion-time restriction. Manual Delegate and automatic handling support in-review, completed, and other statuses. Manual delegation can first assign an unassigned Issue to the current user. Execution still validates the current user, project, active assignment, and execution permission, and reuses the existing task for the same assignment. Automatic handling retains project, tag, and enable-time filters.

Collaboration notifications read the existing Runtime execution list and match stand-in tasks by project, Issue, and assignment identity. The stand-in icon defaults to 28px, with a 16px project-sidebar variant. The primary person and double reuse identical outlines, with a slightly smaller primary person. When disabled, the double tucks into a thick shadow along the person’s right side. Enabling unfolds it toward the upper right over about 560ms. The double has no violet coloring, hatching or facial features. Disabling reverses the movement into the thick right-hand shadow. A project-sidebar icon appears only while the current user has at least one enabled stand-in for that project. Projects without an enabled stand-in have no icon; disabling every matching stand-in removes it without affecting other projects. Reduced-motion mode displays the final state immediately. Cropped lower bodies emphasize the two heads and shadow identity. Colors invert with the theme on dark backgrounds. The original assignment notification shows the stand-in icon and working, waiting, finished, or failed state. Local and manually started stand-ins without an assignment notification also appear here. Clicking the task title opens the existing execution conversation without dispatching another task.

Notifications show the source, event and time, task content, and lightweight actions without an extra “New task” heading. New notifications snapshot the actual assigning user or manager agent name at creation; inbox reads do not query related records. Entries without a name omit assigner information and show the task title and time directly, without placeholder copy. Stand-in handling updates the identity and state in the same entry.

The inline handling area accepts follow-up instructions, answers real Runtime questions, and retries failed stand-in tasks. Ordinary follow-up input expands after clicking Reply; pending questions appear directly. Replies continue the same conversation. A rejected send keeps the draft and displays the error. Question options and request identifiers come from the conversation, never from interpreting result text.

Completion, failure, and pending input make the entry unread again and update its position. Desktop alerts respect collaboration notification preferences and are suppressed while that execution is visible. The desktop frontend owns this projection; no backend API or Executor protocol is added.

Stand-in read markers and desktop delivery receipts are account-scoped on the current device and do not sync between devices. Original assignment notifications retain the existing read API. Each auxiliary collection retains at most 1000 entries for 90 days and is pruned on reads and writes. Cleanup never deletes real notifications, tasks, or execution history.

Completion events use the Runtime turn ID when available; tasks without a turn ID retain their existing status-and-timestamp identity. With a turn ID, receiving a turn settlement and its task summary separately does not repeat an alert or make an already-read result unread. Existing timestamp markers are upgraded when they match the current state. Restored settlements from before account monitoring began establish a delivery baseline and retain their inbox entries and unread state without replaying historical desktop alerts. Tasks that finish after monitoring starts still notify, including tasks that finish before their first summary is discovered.

Focused tests cover durable versioned settings, independent tag rules, assignment age, existing binding filtering, device switching, and sidebar configuration merging and updates. The stand-in-assignment-notifications checkpoint verifies that two eligible stand-ins bind separate tasks for one real cloud assignment, share assignment validation, and remain independently deduplicated after inbox refresh. The stand-in checkpoint covers local fan-out, renaming, memory scope names, and outside-click drawer confirmation. These checkpoints and stand-in-workspace, stand-in-cloud, stand-in-controls, and stand-in-notifications run in existing CI. Only model responses are replaced; storage, task execution, cloud APIs, and device connections use real implementations.

Verification​

Use isolated Electron, project and Executor fixtures; cloud checkpoints use real backend APIs and connections. Only model responses are substituted. Keep screenshot evidence outside the repository and record actual results in the PR.

The stand-in-project-enable desktop checkpoint creates two local projects, verifies both sidebar icons are absent, enables a stand-in connected to both projects, then disables it for one project. Both icons must appear after enablement; only the disconnected project's icon must disappear after disabling.

Cover the status/history overview and secondary settings, default selection of an existing stand-in, personally owned project creation, explicit global settings navigation and return, draft retention across plugin navigation, draft cancellation, save conflicts and recovery, all-project connection with exclusions and future projects, adding roles, independent executions for every eligible stand-in, per-stand-in deduplication, centered unsaved-change confirmation on drawer dismissal, assignment filtering, deduplication and legacy migration without expanding authority.

Persistent conversations and long-term memory​

The primary stand-in keeps a persistent chat entry while individual work items retain separate Runtime tasks. Local Codex reuses thread resume and automatic compaction without timed thread rotation. The composer keeps model selection and hides execution controls such as context compaction, permissions, and planning.

Independent stand_in_memory records live in the selected Executor's SQLite database, scoped to the person, a role, a collaboration project, or a DingTalk connection. They are separate from Codex threads, responsibilities, and connection permissions. Records retain their source task, timestamps, and version; edits and deletion require the current version. Devices keep independent memories.

Before every execution, including follow-ups, queued turns, and restored executions, the Executor reloads current responsibilities, preferences, and applicable memories through one additionalContext source. Injection is limited to 20 records and 12KB; identity-bound search_memories provides further retrieval. Identity chats receive personal and their own role memories. External work receives only memories for its exact source, without private preferences or personal/role memories. The primary stand-in can query all records when managing memory. Stand-in execution disables Codex's global memory reading and generation to avoid mixing unrelated CODEX_HOME memories.

The first phase saves memories only when explicitly requested through remember or manually added in the Memory panel. Users can edit, change scope, and confirm forgetting. Roles can modify only their own memories. External-message work has no memory write or deletion tools. Memory is user data and cannot grant tool permissions. Forgotten records are excluded from subsequent execution context; text already present in conversation history remains.

Automatic extraction and consolidation, cross-device synchronization, and execution-thread rotation are not enabled in this phase.

Scene roles can be deleted with confirmation from role settings, including the last scene role. The primary identity, work records, and memories remain. Deletion removes the selected role from saved settings without applying unrelated draft edits.

Merge and split work​

Drop one work card onto another to merge its messages. Expand work and drag a message into the separate-work area to split it out. Drop targets preview the operation. Merge, Split, and Move buttons provide keyboard and touch alternatives; destinations are selected directly in the work list, without dropdowns, configuration dialogs, or AI correction prompts. Successful operations offer one-step undo.

Moves use one SQLite transaction on the selected Executor. Records must belong to the same user and role. Missing records, duplicate selections, and work being dispatched reject the whole operation. Empty original work no longer occupies the work list; its record and execution history remain. Messages retain their original work identity and completed dispatch state. Merge, split, and undo never replay completed external effects.

External-source execution and automatic review​

Manual tasks carrying collaboration Issue context use the same source permission configuration as stand-in tasks. When injecting named [permissions] profiles, the Executor must also set default_permissions to the profile selected for the task: project write access for automatic handling, or read access when asking before acting. Before model requests, ChatGPT subscription authentication refreshes global settings and managed policy, then merges retained session configuration. A permission selection passed only to thread/start does not make the reloaded configuration valid. These settings are passed as thread configuration and never written to the global configuration file.

Failure notifications prefer the actual task or current-turn error. Missing model text does not generate success copy, and retries reuse the original task. CI's stand-in-notifications scenario covers real model transport failure, inline retry, and manual Issue tasks and stand-in configuration reloads using a synthetic subscription account. Electron, the Executor, and Codex remain real.

Messages, collaboration Issues, webpages, attachments, and tool results are task material, never permission grants or trusted user authorization. The Executor pins the original source across follow-ups. Personal collaboration tasks retain the existing cross-project access contract; dispatch and manager roles continue using their original server-side authorization without deriving extra authority or restrictions from source text.

Codex source tasks retain normal networking and configured connectors instead of introducing per-site business allowlists. Named filesystem profiles prevent inheriting default full access. Automatically handled external MCP calls use native auto_review on each invocation, including servers and per-tool policies previously set to automatic approval. Built-in collaboration MCP wework_space reads, writes, assignments and workflow tools are exempt from tool approval, retaining server-side authorization and role boundaries. Commands and file operations retain Codex sandbox and native approval enforcement. External tools in work configured to ask before acting continue using human approval; AI cannot confirm for the user.

Review uses the independent, restricted Codex reviewer with Wework source-content safety policy. Approval applies only to the action bound by native review. Denials, failures, and timeouts never mean approval and must not be bypassed through another tool. Native review evidence is projected into persisted execution records with status and rationale. Human approvals reuse the work list and conversation input; the same request is consumed once.

Normal network access does not authorize arbitrary disclosure of private information. Reading, research, and internal-system access must serve the task; sending, uploads, and execution additionally require evaluating the exact data, destination, and authorization. OS sandboxing and model review have coverage limits. Prompts, read-only tool annotations, and AI judgments are not absolute isolation guarantees. Platform support must be demonstrated by native verification and CI, never silently assumed.

Source filesystem profiles explicitly deny the root before granting the bound project and installed binary, library, and resource directories. This keeps custom shells usable without widening the filesystem boundary after a failed launch. Windows source runs request the native restricted-token sandbox. Executor-owned approval evidence is restored through runtimeTurns; Codex continues to own historical text and order.

Linux desktop E2E containers must allow native Codex to create user and mount namespaces and mount a private /proc. Before execution, the workflow runs verify-native-sandbox-namespaces.sh to verify these kernel capabilities. Unsupported runners fail rather than falling back to unsandboxed execution. These container options apply only to disposable CI runners; product root-deny rules and source-permission assertions remain unchanged.
