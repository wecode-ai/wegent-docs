Phone-local executor

Phone-local execution reuses PC Wework's local executor, Codex app-server, and Runtime RPC. It does not register a synthetic cloud device or forward local tasks to a remote machine. The current embedded implementation targets ARM64 iPhones. Android needs its own native execution backend; iOS validation does not establish Android support. Codex sends model requests according to the user's selected provider and model configuration.

Local-first startup and optional Backend​

The app opens directly into the existing task list without requiring Backend login. Builds with the native module prepare local execution automatically; view status or retry in “Settings → Local execution”. Device filters are hidden before Backend login, and new conversations run on the phone by default. Existing conversations retain their execution device; the new-chat layout is unchanged.

“Settings → Models and accounts” provides official OpenAI browser login, an explicit device-code option, and custom Responses models. API Base URL, model ID and API Key use device secure storage. Runtime configuration and real tool-call connection probes reuse the PC implementation. Custom models support only Responses. Desktop Codex credentials are never read.

Configure the Backend address in “Settings → Sign in to Wegent” and complete the existing authorization to enable Backend models, authorized cloud devices, and device filters. Backend models can also execute on the phone: model service location and execution device are separate.

Local availability comes directly from the current phone environment's native supervisor, independently of Backend device requests. Cloud responses and cache restoration cannot overwrite current native state. After stopping the runtime, the phone is unavailable for new conversations. Inventory composition and response ordering follow PC hybridServices.ts and useWorkbenchDataRefresh.ts.

Data and process ownership​

  • PC references are wework/electron/src/runtime/managed-executor-runtime.ts, runtime-supervisor.ts, and runtime-supervisor.process-group.test.ts. Device, workspace, task, and request fields retain existing executor semantics.
  • Model selection and execution permissions come from packages/chat-core/src/local-runtime-model.ts and local-runtime-execution.ts. Composer references come from runtime-composer-references.ts.
  • The phone filesystem, executor directory, Codex authentication and local models belong to a persistent phone profile. Backend login, logout and account changes neither remount local data nor stop local work. Browser and device-code authentication uses the official app-server protocol; completion must match both the login ID and process generation so an old process cannot overwrite a newer login.
  • The executor owns transcript persistence. The native event journal only bridges notifications while JavaScript is suspended; it does not replace task history or replay across phone environments.
  • Upgrades adopt an existing environment without moving, merging or deleting roots. Multiple unselected legacy environments require explicit selection in “Settings → Local execution”. Native discovery reads only valid root metadata, never authentication or chat contents.
  • Cloud HTTP, Socket.IO, device caches and file previews are scoped by Backend address and user. Account changes revoke old requests, sockets and remote file caches while preserving phone previews and reading positions. Each cache scope must finish hydration before writes are enabled, preventing empty startup state from overwriting offline history.

Screen lock and foreground recovery​

Running status alone does not establish request-channel health. Native diagnostics on foreground / network changes and request timeouts read pipe byte counts, guest accept calls and failures, the last host errno, guest PID, listener restoration success/failure counts, and restoration errno. They never consume pipe data or record request / response contents. Physical-device requests and incremental output must verify recovery; running status or a successful TCP connection is insufficient.

Screen lock suspends the app's periodic memory sampler. When a guest allocation finds a sample older than two seconds, admission synchronously reads actual host memory before applying the existing pressure, headroom, and hysteresis rules. A paused timer is not evidence of memory exhaustion. Failed or invalid host reads, real pressure, and allocations exceeding the total allowance still fail closed. The synchronous provider must not log or acquire guest locks: its caller may already hold a memory or syslog lock.

iOS can reclaim TCP listening endpoints during suspension. Device diagnostics show repeated host EAGAIN from accept while all RPC methods time out without pipe backlog. Host fault injection with the same executor establishes that combining listener POLLHUP with accept EAGAIN makes Tokio retain closed readiness and spin the accept future, starving request handling. Injecting EAGAIN or ECONNABORTED alone does not reproduce the complete stall.

Physical iOS readiness also depends on the requested mask: the same failed listener returns no events for POLLIN, but returns POLLHUP for POLLIN | POLLOUT | POLLPRI. Restoration and guest readiness must consume the same full-mask sample, rather than checking a narrow mask before an independent broader query. Accept uses the full mask as well. Successful restoration discards old endpoint events and lets the refreshed reactor wait for connections on the new endpoint.

The embedding enables TCP listener restoration before exposing host closure to the guest reactor or accepting. It recreates the saved address, actual port, backlog, successful socket options and file flags while preserving the guest open-file identity and host descriptor number. A descriptor generation change re-registers each poll/epoll backend and clears stale edge state; fired ONESHOT registrations still require explicit guest rearm. Successful explicit guest shutdown disables restoration. Restoration failure retains the actual error without unbounded retries. This platform adaptation preserves PC RPC, task identity and event contracts without restarting the environment.

regress_listener_recovery.c fault-injects host reclamation for IPv4/IPv6, two consecutive cycles, multiple poll sets, dup registrations, ONESHOT, retained ports/options/flags, actual connections after restoration and observable failures. This test and the real executor/HTTP recovery probe are host verification, not a substitute for physical iPhone screen-lock and streaming acceptance.

Recovery registers a thread once per blocking call and unregisters it unconditionally on return. It must not count sockets in the poll set: another thread can add or remove descriptors through epoll_ctl or close while the wait releases the set lock. Traversing different before/after sets leaves released tasks in the recovery list, causing a loop under the recovery lock that blocks all RPC. regress_poll_waiters.c synchronizes two real threads at the host wait boundary to cover membership addition, removal and replacement. It fails deterministically on the old kernel and requires registration cleanup before a waiting task is released.

Guest process lifetime must not depend on inactivity. Codex app-server may wait indefinitely for stdin, and suspension advances monotonic time without guest progress. The old iSH poll timeout branch called do_exit_group(0) after 60 idle seconds while still holding the poll mutex, leaving the last worker blocked in descriptor cleanup on a departed owner's lock. Remove that idle-exit policy while preserving explicit exit and signal handling. regress_idle_poll.c ages a real guest's progress timestamp by 120 seconds and verifies bounded wait, process survival, subsequent event delivery and explicit close. It fails deterministically with the old library and passes with the corrected library.

Failed history reads remain distinct from successful empty history. Failure updates only the sidebar avatar retry badge and preserves visible messages. An unsuccessful initial read shows neither new-conversation onboarding nor an empty-history claim; only a successful empty read shows the empty state.

On foreground entry, wait for any ongoing native shutdown, ensure the environment previously requested to run is started, and then reconcile the event journal and active transcript. Recovery does not resubmit user messages or refresh project or conversation lists. Explicit stop revokes running intent; disposing an old JS instance during environment selection cancels its pending startup. Startup and shutdown failures remain visible and never become fabricated readiness. The startup barrier follows PC wework/src/desktop/localExecutor.ts and wework/src/api/local/localServices.runtimeReadiness.test.ts.

Shutdown and explicit phone environment switching​

Wegent logout revokes only the cloud connection. The drain sequence below applies to stopping local execution or explicitly confirming a preserved phone environment switch in “Settings → Local execution”. Backend account changes never trigger it.

The main process exiting does not prove that its descendants and host threads have stopped. The compatibility patch removes upstream do_exit_group logic that removed live threads after a timeout, deferred resource release, and reported a completed exit. Live threads stay in the group. The leader becomes a reapable zombie only after the last thread releases its own resources. Threads clear TLS current before allowing a parent to reap their task, preventing pthread cleanup from dereferencing freed memory.

Native entry points increment the host-thread count before pthread_create, undo it on creation failure, and decrement it at the end of the outermost cleanup handler. A nonzero count prevents mount switching. Timeouts must remain visible failures. Never use host _exit() or host signals to terminate the entire app. Startup, extraction, login, and shutdown failures disable only the local capability; remote features must remain openable.

Execution permission boundary​

The App sandbox and current account mount bound local files. The runtime does not implement complete Linux namespace, seccomp, or Landlock isolation.

The native host owns the mount table. Guest mount and umount return EPERM, preventing host-path exposure through the real filesystem and mounts that survive environment switches. Host fakefs, proc, and devpts setup remains available. An attachment explicitly targeting the phone must fail when that environment is unavailable or mismatched; it must never use Backend upload instead.

Tasks within one phone environment have no workspace-level security isolation. Full access can read other projects and Codex authentication files in that environment. Original API Key settings use Keychain, but execution still supplies credentials to the guest runtime. Treat untrusted repository scripts accordingly. The emulator shares the app process, so native crashes or extreme memory pressure can terminate the app. Memory monitoring is not process fault isolation and does not impose disk or CPU quotas.

The pinned official Codex 0.167.0 runs in this environment, but its restricted Linux sandbox does not:

  • readOnly and workspaceWrite commands fail. Never automatically elevate them.
  • The bundled bubblewrap --version succeeds. A minimal isolation command, bwrap --ro-bind / / --unshare-user --unshare-pid -- /bin/true, fails at prctl(PR_SET_NO_NEW_PRIVS) with EINVAL.
  • The pinned iSH source lacks the corresponding complete namespace and seccomp implementations. Its supported clone flags also exclude namespace creation. Returning fake success for these calls would create a false security guarantee.
  • Command validation uses explicit dangerFullAccess. The product must require the user to select permissions that match this capability; it must not claim read-only or workspace isolation is enforced.

Upstream references: Linux PR_SET_PDEATHSIG, PR_GET_PDEATHSIG, and pinned iSH source.

Pinned source and builds​

wework-mobile/modules/wework-local-runtime/native/ish-source-lock.json pins the upstream revision and SHA-256 checksums for the patch, licenses, probe Alpine image, and Codex npm package. The preparation script verifies these inputs and the complete applied patch in existing checkouts. Other revisions or local changes are rejected.

uv run --no-project python \
  wework-mobile/modules/wework-local-runtime/scripts/prepare-ish-source.py \
  --output /external/ish-source

node wework-mobile/scripts/build-local-executor.mjs \
  --repo "$PWD" --output /external/executor-cache

uv run --no-project python wework-mobile/scripts/build-local-runtime-ios.py \
  --source /external/ish-source \
  --rootfs /external/clean-rootfs.tar.gz \
  --rootfs-sha256 VERIFIED_ROOTFS_SHA256 \
  --executor /external/executor-cache/wegent-executor \
  --output /external/ios-runtime --link-module

The executor toolchain pins Rust 1.94.1, Zig 0.15.2, cargo-zigbuild 0.23.0, and OpenSSL 3.5.9. --openssl-archive accepts a previously downloaded archive with the same mandatory checksum validation. iSH uses guest_arch=arm64, engine=asbestos, jit=true, and jit_emit=false: the former enables the AOT-capable engine; the latter disables runtime executable-code generation.

The production rootfs is a separate, explicitly supplied and hash-verified artifact containing Alpine, bash, git, CA certificates, and the complete official Codex resource directory. The build script adds the current Rust executor. Do not copy meta.db directly from an active development rootfs: fakefs inode mappings refer to host files, and moving them can break symlinks. Use upstream fakefsify / unfakefsify import and export, then verify an independently imported directory. Delivery archives must have empty /root and /tmp directories, with no probes, logs, account data, or session files.

Keep large files, toolchain caches, static libraries, rootfs archives, logs, and installation artifacts outside the repository. The module's generated vendor link is local build state and must not be committed.

Focused validation​

Initial phone reads are independent of Backend connection and discovery. Pull-to-refresh reads only the selected work list; the all-device view reads visible devices concurrently, keeping phone access while disconnected. The separate device-discovery action does not chain model reads, transcripts or executor restarts. Late disk-cache hydration publishes from the merged authoritative device snapshot, preserving fresh phone data. Read failures remain at the sidebar avatar retry badge; this does not introduce automatic list refreshes.

When the diagnostic logs setting is enabled, startup diagnostics extract only fixed, allowlisted checkpoint codes from executor stderr for model catalog preparation, Codex startup, and conversation reads. The system log associates them with the runtime generation. The parser retains at most 128 bytes per line and discards all fields and unknown logs; raw stderr, authentication data and message bodies are not persisted. Checkpoints do not change requests, retries or runtime lifecycle behavior. Disabled diagnostics still drain stderr to avoid pipe backpressure, without parsing checkpoints.

Diagnostics, storage, and performance​

The native iOS / Android switch in Settings → Diagnostics defaults off and persists its value; a failed change retains the previous preference. It controls app layout, connection, native supervisor, and iSH host log output. The kernel retains its bounded 1 MiB in-memory ring and memory safety sampling remains active. Codex and the OS may still retain error logs; the switch does not disable all third-party disk writes.

Event replay uses memory only, retaining at most 2048 events and 8 MiB of serialized data. It evicts the oldest events; oversized events remain live-deliverable but are not cached. Gaps explicitly return truncated for the existing transcript recovery flow. This is not a bound on total process heap usage. The executor still persists complete conversations; the supervisor no longer writes a duplicate events.jsonl, and layout diagnostics no longer rewrite a periodic file.

Local startup removes obsolete generated diagnostic files. After all guest processes have exited and before launching a new one, guest fakefs APIs reclaim only canonical UUID-v4 model catalog files generated by ProcessCatalog. Directories, symlinks, custom catalogs, credentials, and conversations are preserved. Cleanup failures produce diagnostics without blocking app startup. Projects, dependencies, conversation history, and third-party caches can still grow with use. Local Codex computation, memory safety checks, and event transport still consume resources.

native/tests contains 22 guest C assertions covering parent-thread death notifications, fork/exec/identity-change semantics, blocked pipe shutdown, EINTR and SA_RESTART on both read paths, and /proc/<pid>/stat for retained zombies and live workers. An additional host probe deliberately blocks a native worker beyond the upstream timeout and verifies that the process cannot be waited or reaped early. Only actual worker termination permits a zero count and final reap. It also verifies rollback of a child that was constructed and exec-loaded but whose native thread never started.

uv run --no-project python \
  wework-mobile/modules/wework-local-runtime/scripts/test-ish-runtime.py \
  --ish /external/ish-source/build-host/ish \
  --fakefsify /external/ish-source/build-host/tools/fakefsify \
  --rootfs-archive /external/alpine-minirootfs-3.21.0-aarch64.tar.gz \
  --output /external/probe-results \
  --native-source /external/ish-source

Use a fresh output directory to avoid overwriting account filesystems. Results go to results.json. The host probe requires Apple ARM64; omit --native-source to run guest assertions only. The runner checks guest exit status and assertion counts because the upstream CLI's PID 1 halt path can turn a guest failure into host exit code zero.

Completed macOS ARM64 validation covers non-JIT iSH, the focused probes, real Rust executor IPC, official Codex initialization, commands, file writes, Git operations, streaming output, cancellation, and shutdown.

An independent native harness on an iPhone running iOS 27.3 on 2026-11-14 verified executor health, Codex config/read through the real executor, shutdown and restart, plus initialization, file writes, Git staging/diff, and real command/exec/outputDelta after directly starting official Codex. The harness uses the same native runtime and rootfs. The direct Codex probe changes only the program entry point in an external test copy; it does not extend the product executor's RPC allowlist. A subsequent probe using the actual UIKit grace implementation completed system expiration, real Codex command cancellation (exit 137 with no subsequent file write), and native shutdown/restart health checks while still in the background. A separate foreground probe completed after 45.088 seconds with backgroundTransitions=0, exit 0, and successful real file writes and Git operations, without premature cancellation. These checks are not the full product task-to-model path. Device model inference, product task streaming, the complete product cancellation flow, and sustained background execution remain unverified. Android remains unverified. E2E and AI verify are not run by default.

The existing CI core:native-lifecycle suite now includes mobile-local-payload.scenario.mjs. It loads the real shared model and execution builders and uses the real executor and Codex for two create/send rounds, checking thread identity, message IDs, and state. Only model SSE is mocked. Syntax, lint, module loading, and CI classification were checked; the new E2E scenario was not executed during this development and does not constitute device coverage.

Validate JavaScript numbers at the JS/native boundary. Expo SDK 57 represents numbers in untyped dictionaries as Swift Double; do not read afterSequence or timeoutMs with as? Int ?? default. That resets nonzero replay cursors to zero, repeats the first page after 256 events, and leaves subsequent live events buffered behind failed recovery. Defaults apply only to omitted values. Reject fractional or non-finite numbers, negative cursors, and unrepresentable timeouts. Native regressions cover multi-page replay, foreground resume cursors, and timeouts.

iOS background execution and distribution​

The current implementation supports foreground execution and uses UIKit UIApplication.beginBackgroundTask to request a short grace period after entering the background. It does not use BGContinuedProcessingTask, fixed percentages, or output byte counts. The system decides whether to grant time and when it expires. There is no promised duration, lock-screen continuity, or background completion for arbitrary-length tasks. Expiration must cancel the actual task and report expired; the executor transcript retains completed content. An artificial background deadline must not cancel a foreground task. Leases still match runtime generations and task revisions so old releases or state queries cannot cancel a newer turn.

The retired Continued Processing probe explains this choice. That API requires timely, measurable progress. Bounded work can update Progress using its real total and completed items. Bytes received from a model with an unknown output length show activity, but do not provide the required completion progress. Never fabricate totals, percentages, or meaningless keepalive activity.

The retired probe set totalUnitCount to -1 while continually adding actual output bytes. On iOS 27.3, expiration arrived approximately 20 seconds after entering the background despite real output every second. System dasd logs explicitly reported Task has not reported progress within expected cadence, marking stalled; the Activity Progress Policy suspended the task, with a recorded fraction of zero. NSProgress defines a negative total as indeterminate, with fractionCompleted always zero. That approach cannot support sustained background execution for Codex tasks of unknown length. Twenty seconds is an observation from this run, not a fixed UIKit grace period or system allowance; other expirations still require system-log diagnosis. Resuming output after returning to the foreground does not establish continuous background execution.

The native event journal bridges suspended JavaScript notifications; it does not grant background execution rights. The product must report uncertainty and expiration accurately. Host tests and bounded-work controls cannot replace device validation of actual model tasks.

Apple references: UIKit background grace, BGContinuedProcessingTask, long-running task guide, Progress.isIndeterminate, WWDC25 session 227, and Apple DTS discussion of unknown-length work. The DTS discussion describes an API primarily suited to fixed-length work; fabricated-progress suggestions must not be used to bypass the system's requirements.

The App Store additional terms address conflicts with store terms only; they do not waive GPL source and license obligations. Distribution must provide the matching upstream revision, compatibility patch, and build instructions. Wegent's license does not replace these upstream terms.
