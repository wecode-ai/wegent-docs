My assistants

In the Chinese interface, the My assistants entry is labeled 我的助理.

Select My assistants in the Wework sidebar. With the Collaboration experience preview on, it opens the new assistant center. Turn the preview off to use the original page and its stop control. Existing assistant configuration, sources, and work history carry across.

Ongoing Issue collaboration​

Assigning an Issue or mentioning a member wakes their enabled, project-connected stand-ins that match its tags and allow automatic handling. You can mention yourself: eligible stand-ins receive the event without a human self-reminder. The same stand-in reuses its conversation for the same Issue. Reassignment retains history but still requires fresh authorization. Reassignment, unassignment, deletion of the original mention or pausing automatic intake still allows continuing and retrying the conversation, including synchronizing public replies. Manually starting a stand-in does not require assigning the Issue to yourself and never changes its assignee. Automatic intake settings select new work without restricting explicit user actions. Current project and Issue access and execution permissions still apply. If the initial startup fails, retry from the original Issue without deleting its conversation or reassigning it. Recovery resumes an existing native session or starts one within the original task. The latest startup failure's code, redacted message and timestamp remain available after retries and restarts in the conversation query's startup_failure field. Substantial assigned work runs in native subagents without requiring an extra delegation request. The default assistant coordinates, verifies and replies concisely; simple questions are answered directly. Normally only a brief acknowledgment and the verified result appear as comments, with material blockers, questions or native approvals surfaced when needed. Routine tool and subagent progress stays internal. You can keep writing and sending while subagents work; follow-up wakeups are handled in order. Reply directly to a stand-in comment without another mention to continue with that role. Private chats, reasoning and tool activity are not published.

Stand-in replies on an Issue show the owning user followed by the role in parentheses, for example “Alex (Assistant)”, so participants can distinguish different users' stand-ins. A user ID appears while the member name is unavailable and updates to the name when member information loads.

Stand-in chat and desktop notifications​

From Collaboration → My work, the right-hand Stand-in tab lists work by role. Select work to continue its original task conversation inline. The home only lists Issue-related work and exposes Assistant settings. Select Chat to talk with the stand-in about collaboration. Board connection guidance remains until an enabled identity connects an accessible board. The home keeps the assistant tab and one Issue detail tab; opening another Issue replaces the current detail, while reopening preserves drafts and private chat is not automatically published to Issues.

Keep sending requests when the previous reply ends or a background result starts another reply. Messages are delivered into the original conversation according to the current turn state.

After sending a message, three dots appear while you wait for the assistant's first reply. As soon as reply text arrives, it appears and the composer returns to its send button. You can send a follow-up while a subagent continues working in the background.

This presentation applies to primary and role conversations on the My assistants page and the embedded primary conversation on the collaboration home. Each native AI message is displayed separately; acknowledgements before background execution and results afterward are not merged. Internal guidance blocks and execution timers are hidden here. Ordinary task and coding conversations retain their execution presentation.

Stand-in identity conversations and collaborative Issue stand-in conversations enable native subagent v2, including resumed conversations. Ordinary tasks retain their default configuration, and explicit single collaboration mode still disables subagents. Native permission, source-scope and approval constraints remain unchanged.

If the execution device is offline or denies access from this device, open Manage assistant and choose another device under Where to run. The selector is unavailable while the change saves.

Open Left sidebar → My assistants, then select an assistant. Your messages appear in filled bubbles on the right, and AI replies appear as borderless text on the left. Summaries of answered ordinary questions are hidden once the assistant replies. While native subagents work in the background, send another message in the same main conversation without cancelling the children or waiting in the ordinary task queue. Failed sends retain their content and attachments. Resolve pending questions and permission requests through their original cards; chat messages never substitute for authorization. Independently tracked tasks are reserved for work that actually needs a separate conversation, workspace or lifecycle, not merely to keep chat available.

The desktop prompt above the composer offers Notification settings, Don't show again, and Dismiss for now. Notification settings opens the OS notification settings on macOS and Windows and the bell's unified Wework settings. Allow OS notifications and check the system channel under Stand-in alerts. On Linux, enable notifications manually in your desktop environment. Opening settings does not establish that permission was granted. Temporary dismissal lasts for the app session; permanent dismissal is account-scoped on this device and hides only the prompt, without disabling notifications. You can always use Top-right bell → Notification settings → Stand-in alerts.

The number beside My assistants counts unread AI messages in primary and role conversations, not internal subagents or task completions. Counts above 99 display 99+. Viewing a foreground conversation acknowledges its messages; hidden or background windows do not. A completed stand-in turn generates at most one desktop notification showing its final reply. Background tasks routed through the stand-in deliver their results in the stand-in conversation. Primary notifications use the title My assistants and open the corresponding device, account and identity conversation. Accounts do not share counts. Messages remain in the conversation and notification center even when OS delivery is blocked.

Organize assistant teams​

Open My assistants → Teams → Create team, enter a name, choose a lead and members, and add team duties as needed. A specialist can join multiple teams, with duties configured separately for each team. Use the primary assistant or a specialist on the current device as lead. Other members can run on their configured devices.

Open a saved team from Teams to give it work. The lead delegates based on the team roster and duties, and results return to the team conversation. Each team conversation has its own history. Changing the lead opens a conversation under the new lead.

From Teams, edit or delete a team. Its assistants remain available individually and in other teams after deletion.

Share an assistant or team​

Open My assistants → Sharing → Share an assistant or team. Choose what to share, search for and select a recipient, then select Send share. Select Allow recipient to copy to enable Copy to my assistants for the recipient under My assistants → Sharing → Shared with me. The recipient configures connections, execution devices, and workspaces for their own assistants.

In Shared with me, select Use directly to start a separate conversation, then select Open conversation to return. The owner maintains the configuration, and the executor reads the current version before starting a new turn. Under Shared by me, select Revoke share to end the recipient’s access. Recipients retain any copies they created.

When two teams include the same source assistant, copying them on the same device reuses the existing assistant copy. When a newer version is available, select Update team or Update to shared version under Shared with me and confirm to apply the new team duties or assistant prompt.

Delegate work to another assistant​

In My assistants, name an assistant when you hand off work. When you leave the choice open, the assistant can assign work automatically if the responsibilities clearly match. If the choice affects the outcome and several assistants fit, the assistant asks first. One request can be split across assistants, and an assistant can hand off a part that calls for different expertise.

Expand a Delegated tasks card in the message history to see roles, progress, and errors. Open Assistant details at the top right to see Active delegations in the popover. Select Tasks and delegations at the top right to see task activity and delegation history in one list in the right-hand panel. After the work ends, the card stays in the message history and the right-hand panel. You can answer supported questions right in the card. Open a task to read its independent conversation and handle native approval prompts. Each role uses its saved model and working directory, and its long-running chat remains available. Results flow back to the assigning assistant, which summarizes them in the original conversation.

Cross-device delegation uses the role's configured execution device on the same Wework account. While that device is offline, the task shows Waiting for device. You can open the task from the original conversation once the device is online and accepts it.

Work that depends on earlier results shows Waiting for prerequisites. When the prerequisite succeeds, its result goes to the next role. A failed or cancelled prerequisite leaves the dependent task marked A prerequisite did not complete. Choose Retry beside a failed branch to run it again in the same task. Other branches keep their progress and results.

Choose Cancel branch to stop one branch and its subtasks while the other branches continue. Choose Cancel delegation to stop every unfinished branch in the request. Completed results remain available. If the execution device is offline, the card shows Waiting for device to confirm cancellation.

Assistant settings​

  1. Open My assistants from the left sidebar, select an assistant, click Assistant details at the top right, then Manage assistant at the bottom of the popover.
  2. In Settings, edit the role's name and handling instructions. Choose an Execution device in the Execution environment section. Select the Execution environment row with the right chevron to choose the model and working directory for that device. Different roles can use different devices without changing the primary identity's binding.
  3. Install/authorize source apps, choose scope and handling mode, then save to enable changes. Calendar/scheduled delegation belongs to this role's connection page, not global cloud connection settings.
  4. Recent activity shows execution records with their status and time. Work opens as a read-only preview inside the same popover; Back restores the list position. Use Open conversation in workspace to reply, approve or use the full workspace. Human questions remain in Needs your input and the original work.
  5. To delete an assistant you added, choose Delete assistant in its settings and confirm the target. Deleting differs from pausing a source; adjust source reception if you want to keep the role but temporarily stop intake.

While the project picker is open, Escape closes only the picker and returns focus to its trigger. The current settings view and unsaved changes remain. A second Escape follows that settings view's existing Back or discard-confirmation behavior.

When opening your stand-in, the page checks onboarding status and shows an inline loading message. Initial setup opens automatically only after the check confirms it is incomplete. Completed setup opens the stand-in directly. If the check fails, use the retry action in the error prompt.

Initial binding discovery shows a loading state, never a premature account-mismatch error. Within the same app session, returning from tasks or boards preserves the loaded stand-in interface while refreshing configuration in the background. Work-list and configuration-proposal polling pause while the stand-in is hidden. Changing accounts or cloud services does not reuse the previous account's page data; an ownership warning appears only after the actual binding has been read.

Open My assistants, marked Beta, in the Tasks sidebar to delegate work, ask follow-up questions, or draft a new assistant with AI. The header displays the default assistant and any assistants you added for switching. The default assistant’s conversation and individual work executions are stored separately. Switching back to the default assistant restores its conversation.

The default assistant can coordinate and delegate work. To add an assistant, select Add assistant in the header, enter a name and optional Responsibilities, then select Add assistant to save. Each assistant has its own conversation. You can talk to it directly or ask the default assistant to delegate work to it. The details popover shows name, intake status, issues that need attention, device and recent activity, without an avatar or outputs section. Recent activity shows work threads and execution timestamps, newest first. The popover previews the three latest records with status icons. Choose View all activity to open the full list. Open Manage assistant → Connections → Calendar to view or edit schedules. Work opens as a read-only preview with Open conversation in workspace at the bottom.

Execution devices and legacy recovery​

Other devices signed in to the same cloud account can see synced assistants. To message an assistant running on another Wework desktop, enable remote personal task access on its execution device. New messages run on the assistant’s configured device.

After connecting your cloud account, open My assistants in the left sidebar to use the account’s default assistant. Clients read the same solo Team and its Bot and Ghost. If the account has no default assistant, Wework checks this device for a saved profile first. After you confirm the import, the assistant opens and keeps its original execution device. If there is no profile to import, Wework starts first-time setup.

Select an execution device in Assistant details → Manage assistant → Execution environment. The cloud account saves your choice for each assistant. New conversations use the selected device. Existing conversations reopen on their original devices. Review the model, working directory and source grants after changing devices.

My assistants offers migration or recovery when it detects an older profile or executor that needs attention. If the executor has stopped, select Resume assistant on this device. Wework stops assistant work on the source device before migration. If the source cannot confirm the stop, you can use the existing cloud definition. Migration keeps conversation history on the source and appends portable profile settings and memories on the destination. Imported profiles remain paused until you configure their working directory and grants.

To export previously detected conflicting definitions, select Default assistant → Assistant details → Manage assistant → Download assistant definition backups.

Click Board in the Tasks sidebar, or select Board from its task view menu, while viewing My assistants to open your personal task board.

The My assistants button in collaboration project headers also carries a Beta badge. Both entries are available without enabling experimental features.

Connect IM conversations​

Send /standin (or /mode standin) in an enrolled DingTalk, Telegram, Discord, or Weibo bot chat to enter assistant mode. A chat without a specific assistant assignment uses the default assistant on your account’s default execution device. Select an online device in Personal default execution environment. When first using a bot, authorize it as directed by the platform and send /bind to enroll the chat. Send /chat to return to Wegent chat or /mode to check the current mode.

New messages enter the selected stand-in’s persistent conversation. When Codex is running, the message guides the current turn. An idle conversation starts a new turn. Messages retain their source and approval requirements. Old task mode migrates to stand-in mode. Its task bindings are removed while tasks and their history are preserved; task titlebars no longer offer Continue in private chat. In stand-in mode, quoted task notifications and task-card follow-ups provide context to the current stand-in without changing its binding or model. Task subscriptions control foreground notifications. Stand-ins and tasks share existing account IM conversations without another recipient choice. Synchronous and asynchronous questions share one interaction: quoting a question answers its original task directly; ordinary messages go to the stand-in, which uses pending questions and recent chat to submit clear answers, handle unrelated requests normally, or clarify ambiguity before submitting.

Manual and conversational configuration​

Select Execution environment in the default assistant settings to open its page. View the device and choose the local project, workspace and model. Back returns to the main settings and keeps your draft. Saved settings apply to the default working directory and model for new work and to the model for new stand-in chat turns.

Open Assistant details → Manage assistant to edit responsibilities and work sources for each assistant. If the default assistant's settings show Private preferences, describe how you'd like it to communicate with you. For example, ask it to reply in English, start with the takeaway, then list action items. After you select Save settings, the assistant uses these preferences only in private chats with you. For work from external sources such as DingTalk groups, it follows Assistant responsibilities. You can edit or clear preferences and save again at any time.

You can also describe a role or configuration change in conversation. The confirmation card appears directly in that conversation with the affected roles, source scopes, and handling policies. Choose Confirm and apply to save and activate the changes. After success, the conversation shows Settings applied and the actual changes; failure retains the card and an error. A group's addition to a role updates that role's connections, not the primary identity's source scope; switch to that role's settings to inspect it. Assistant details → Pending settings opens the same proposal. Closing that dialog neither accepts nor rejects it, and the conversation card remains available. Continue discussing to revise it, or choose Dismiss. A stale proposal cannot overwrite newer settings.

The main surface keeps the conversation, composer, assistant switcher and Add assistant button, with Assistant details at the top right. The top of the details popover shows the work intake setting. It also shows execution-device status and recent activity. Configure work sources in Manage assistant. Connection, device, or background processing issues appear under Needs attention. Select Details to open Connection and processing status and see the full list and available retry actions. Pending configuration can also be opened from the top of the popover. If the background assessment was denied because the account did not match, select Check cloud connection to review the connected account in Settings. Return to Connection and processing status to check again. The question-mark icon at the top right of the details popover opens Usage examples; View all activity opens the complete list. Settings show Memory directly, without those extra entries. Stopping is separate at the bottom left of the settings panel. Settings, Connections and source details have explicit entry and parent-return controls; clickable Settings navigation paths return to Settings or Connections without bypassing unsaved-change confirmation. Proactive background updates retain their own marker.

Proactive background notifications​

All connected sources share the same notification policy: surface important information relevant to you, urgent matters, or evidence-backed possible progress anomalies, even when no user action is required. Explain what happened, why it matters now, its source and timing, distinguishing facts, inference and uncertainty. A possible anomaly need not be confirmed, but must have a concrete signal relative to known expectations. Missing updates, unknown current status of an old problem, or urgent wording alone do not justify a notification. Never resurface resolved or superseded problems as active risks; important new milestones or outcomes can still merit a finding.

Assess related events together and consult recent notifications across batches; notify again only when new evidence changes significance, urgency, the progress assessment or the required response. Routine updates and redeliveries remain quiet; never broaden access or create verification tasks merely to manufacture a notification. Preserve account/source identity and source-provided topic identifiers for correlation; never invent missing identifiers, and use available evidence for semantic assessment. This is a model-driven policy, not an independent guarantee of live state verification. Explicitly requested reports, reminders, scheduled arrangements and authorized work execution retain their existing flows.

Inspect, edit and forget stand-in memories​

Assistant learning is an experimental setting for each identity and is off by default. Show experimental features in Settings → General → Experimental features, then open My assistants → select an assistant → Assistant details → Manage assistant. The Assistant learning section at the bottom contains the switch and Assistant learning report. Save after changing the switch. You can view existing reports after turning learning off. Hiding experimental features hides the whole section and keeps the saved learning setting. Manage source scope, automatic replies and send approvals in connection settings.

The memory consolidation arrangement reviews each identity’s own conversations and authorized sources that can provide review evidence, including work Issues it can access. Inbox messages and subscribed GitHub or GitLab discussions can supply source observations. Connections that provide only collection events can contribute the original records already received for this role under its current grant. A status-only subscription can contribute the status events it received. Native records with verifiable authors and context can support demonstrations, praise or corrections. Your own answers can serve as demonstrations even when the stand-in sent nothing. The runtime rechecks access when reading and saving evidence. Verified public comments on cloud work Issues can establish rework. Only their associations are retained, so the report can recheck current project access.

In Manage assistant → Memory for the selected identity, choose Today’s review or Past 7 days. The review groups lessons into Needs improvement, What worked, Your examples, and Source observations, using the local date when feedback occurred. Open View work example to inspect the source text, or choose All memories to edit or forget a record.

The same review distinguishes confirmed rework from the cross-version rate. A delivered assistant response and your verified follow-up correction, clarification or replacement on the same request establish one reworked request. Repeated corrections to that request count once. The rate also requires the Ghost and Memory versions used for the reply and 24 hours of fully reviewed history. An inbox-only connection, a mentions-only group, a missing page or an unverified author cannot establish zero rework. For Codex, the Memory version includes memories supplied with the turn and additional memories retrieved before sending. Claude currently lacks equivalent evidence of context delivery.

The comparison uses conversations handled by the same role under both versions. It shows the number of answered requests per version and the median change in rework rate across matched conversations, with a 95% interval. When sufficient records exist, you can also compare Memory versions under the same Ghost. Versions identify the actual content used, so reusing identical content counts toward the same version. These figures cover answered requests. Total unanswered demand and your overall workload remain unknown. Both review tabs show the cumulative comparison. They also show the last background verification time when it matches the currently visible result. Verification runs silently.

Reply examples and source observations from the past seven days can inform subsequent replies. Older records can still be reviewed or forgotten while their sources remain authorized. Each account retains up to 1,000 reply examples and 1,000 source observations. When either limit is reached, a new record replaces the earliest collected record of the same kind. Ordinary memories have a separate capacity.

Once independent examples are available, the execution device compares trial answers from the current and proposed role instructions in isolated model sessions. With enough independent cases, the stand-in uses up to six to draft a revision and up to six others to test it. A candidate that passes the first comparison is checked again with the same answers in reverse order. At least one case must improve in both orders, with sufficient evidence and no regression in any case. Open Pending configuration for that identity to inspect the text changes, evidence and comparison. Accept to apply a revision, or inspect and undo the latest applicable revision in Manage assistant → Assistant learning report. Source work can use the default assistant's responsibilities, while private preferences are used in identity conversations. Turning learning off stops new examples and evaluations. Saved memories remain manageable. Offline comparisons currently require a Codex model on the execution device.

Open Manage assistant → Assistant learning report to see completed iterations on the identity’s execution device, its current instructions score, the latest before and after scores, and the improvement status. Scores weight wins and ties across independent cases on a 100-point scale. The after score describes the candidate. The current score reflects that candidate once you accept it. Scores are unavailable without comparable results.

After enabling and saving learning for the assistant, select Run one learning round in the report to start an evaluation using that assistant's collected examples. Select Refresh report later to see the result. Background review continues collecting new examples. The report tells you if there are too few examples, the available examples have already been evaluated, or a round is already running. Suggested changes still require acceptance.

Capability retest shows intent, verification, judgment, actionability, and clarity on a 100-point scale. Each dimension uses its own set of comparable cases. The report uses a radar chart for three or more scored dimensions and comparison tracks for one or two. Insufficient evidence and not applicable appear as separate states, and a measured zero appears as a score. The overall blind verdict determines whether the assistant proposes an improvement. When the proposal is available for review, select Review improvement in the report. You can also review pending changes in order from Assistant details → Pending configuration.

The default assistant memory panel also lists unreferenced Legacy forgetting fingerprints under Forgetting rules, with their time and short identifier. Older versions retained neither fact text nor scope, so these show Unknown scope without reconstructing content. They are never supplied to models or shown in project-specific panels. Choose Delete rule and confirm to remove only that fingerprint; one old memory may have multiple fingerprints, and other restrictions remain. Fingerprints referenced by current rules cannot be removed separately. Concurrent changes require reloading before deletion.

You do not need to say “remember this” every time. The stand-in can extract lasting information from currently authorized ordinary conversations, such as stable preferences, recurring constraints, long-term goals and reusable decisions. Quotes, hypothetical examples, assistant suggestions and other people's facts must not automatically become facts about you. Source content never grants new permissions.

Conversation review uses visible user and assistant text and native records from authorized sources. Raw tool traces and hidden reasoning do not serve as native source evidence.

Memory search uses response-size-bounded pages. Oversized records are read in chunks rather than skipped or allowed to block later memories. Changes to records or their visibility invalidate continuation and require a fresh search; old and new pages must not be combined as one piece of evidence.

Pausing new-work intake for the stand-in or a role does not revoke saved source grants; those sources remain available for memory. Pause the memory consolidation arrangement to stop consolidation, or remove a source grant to revoke access. Automatic consolidation exposes only source- and run-validated memory reads, saves and progress tools, never Shell or external writes.

Memory consolidation tasks are hidden from the left task sidebar, including running and finished records. Open My assistants → Default assistant → Assistant details → Manage assistant → Connections → Calendar → 助理记忆整理 to view run history and open the original task. Hiding these tasks does not affect background consolidation or saved history.

Memory consolidation and Assistant learning run silently in the background. Open the calendar for run results and the identity’s Pending configuration for suggested role revisions.

Conversation and external connection histories are read separately. If an external source is unavailable, review can continue for other sources and resume the unfinished source in a later run. To investigate, look up the calendar run ID in the execution device logs under stand-in memory connection for the source type, read stage, elapsed time, and error code.

After the default assistant is enabled, its execution device provisions a 助理记忆整理 (memory consolidation) arrangement once, checking every six hours by default. Open My assistants → Default assistant → Assistant details → Manage assistant → Connections → Calendar → 助理记忆整理 to inspect its schedule and run history, pause, edit or delete it. Background provisioning does not recreate a paused or deleted arrangement. Consolidation uses an independent conversation, leaving the current chat free; the execution device and model must be available. Open the original task from its run history to inspect the result. Consolidation does not automatically start a primary conversation with ordinary tool permissions just to report completion.

Background consolidation preserves evidence and scope, following conversation pages and long-message continuations. Incomplete reads or failed saves must not advance a conversation's completion watermark. After correction or forgetting, consolidation does not reconstruct that memory from the same old evidence. Forgetting does not delete the original conversation. As selected by the user, minimal forgetting rules also retain the compact excluded fact and its scope, not original conversations, files or evidence excerpts. Rules are not active memories: stand-ins read them to avoid relearning the same meaning without excluding new facts about the same topic. Exact fingerprints are enforced by code; semantic comparison across paraphrases is model-mediated and does not guarantee recognition of every equivalent statement. Expand Forgetting rules below the memory list to inspect compact facts and scopes. Choose Delete rule and confirm to allow future learning; cancel makes no change. Deletion neither restores an active memory immediately nor changes other rules. Failed reads or deletion preserve existing data with a separate reload action. Native semantic behavior across paraphrases still requires verification.

Records with a saved excerpt show View source evidence. Expand it to inspect the excerpt, source identifier and whether it is a user statement, assistant statement or source record. An assistant statement is not a user fact. Records without saved evidence do not show this control. Expanding it neither rereads the source nor changes the memory.

Editing a memory's content or scope in the panel clears its old evidence association; background consolidation can attach matching evidence later. Opening a record or saving it without changing its content or scope preserves its evidence.

Open left sidebar → My assistants → Assistant details → Manage assistant → Memory and check the selected execution device.

Model selection​

Stand-in profiles support cloud models and custom models configured on the execution device. Cloud models use that device's connected Wework cloud account; local custom models use its provider configuration and authentication. Concrete work created by a stand-in uses the saved model selection. After switching execution devices, confirm that the selected device has the required model configuration and access.

In My assistants → select an assistant → Assistant details → Manage assistant → Execution environment, open the execution settings, choose a model and reasoning effort, and save. My assistants chats use the updated profile settings from the next message. The current turn continues, and existing work tasks keep their working directories and sessions.

In Collaboration → My work → Stand-in, select Chat and use the composer’s model selector to switch models temporarily. Before the first message, the selection applies directly. Execution devices that support thread-based routing switch providers in the original session, preserving its identity, history and draft. Older devices may show a compatibility prompt and start a new session on the next message. Finish the active turn before switching. Temporary selections apply only to that chat.

Stand-in chats currently require the Codex runtime for operation approvals. If the profile uses a Claude Code model, select an available Codex model in the execution settings and save before continuing the chat.

If the current model is unavailable, select Reload models in the chat. When an older session’s provider cannot be read or is incompatible with the profile model, select Continue in a new session. After confirmation, your next message starts a new session in the same stand-in chat and preserves its history and draft.

Assistant task permissions​

Open My assistants → select an assistant → Assistant details → Manage assistant → Execution environment. Under Default task permissions, choose Read-only, Workspace, or Full access, then save. Read-only is the default. Full access uses the same confirmation and high-risk command approval options as ordinary conversations.

When an assistant creates a Codex task for work you initiate, the task starts with the assigned assistant’s saved mode. Open the full task conversation to change its mode in the composer. The change takes effect starting with the next turn you submit. Resolve approvals for the current turn in their original cards. Existing delegations without a selection default to read-only. Background follow-ups and work triggered by an Issue, connection, or calendar use their own execution policies.

Moving an assistant to another execution device resets its default task permissions to Read-only on the receiving device. Save the move, then open the assistant on that device to choose its default task permissions.

DingTalk and collaboration sources​

The shared DSH EventBus schedules connection collection for the assistant, the GitHub and GitLab sidebar, and task subscriptions. The host combines duplicate collection requests, provider plugins read their resources, and the Executor stores each subscriber’s cursor and delivery receipts. A source collection is cancelled after 15 seconds. The conversation manages any model turn it has already accepted.

Connections groups sources under Configured and Available. Each source appears once with its receive scope, status, and next action; other sources remain visible. A configured scope does not mean intake is active: projects retain their scope summary when Receiving is off. Calendar has a separate Scheduled work section.

Search by app name or configured scope name at the top, or select the configured count to show existing sources only. Select All sources to restore the full catalog. The count is per source, and filtering does not change the stand-in's configuration.

Under My assistants → Assistant details → Manage assistant → Connections → Collaboration projects, select Add a receive scope → Projects and independent issues to search and select specific projects. You can also receive work from all projects you participate in or exclude specific projects. Select the separate Independent issues checkbox to receive independent issues assigned to you. To receive issues that list you as a participant across projects, select Issues I participate in under Add a receive scope. Receive all covers these scopes and future projects you participate in. Project issues can trigger on assignment. Cloud projects also support comment mentions. Each assistant handles events that match multiple scopes only once.

Open a source to install its plugin or sign in, then choose the receive scope and handling. Sources on remote execution devices require authorization on that device. Existing scopes remain visible and removable when a source is unavailable. When a mailbox account is deleted from this device, its existing scopes in other stand-ins show “Mailbox account unavailable.” Add the account again and choose a new receive scope to resume receiving. Returning to Connections or the role settings home retains the draft; save to apply it, or cancel and confirm discarding it. Press Enter to add a project tag. Unfinished or overlong tags prevent saving and retain the input; leaving or disabling intake requires confirmation before discarding the draft. Scope and handling changes take effect after saving stand-in settings; verifying a mailbox account also requires saving those settings before receiving new mail.

For GitHub and GitLab, after signing in, select Add a receive scope, then choose Personal events or Repository events. Select an account for personal events, or search and check individual repositories. For self-managed GitLab accounts, enter the instance address. Scope changes remain drafts until you save the assistant settings.

After verifying a mailbox, select Add a receive scope and choose an inbox. New mail starts arriving after you save assistant settings.

Connect DingTalk​

Onboarding and both types of assistants share the DingTalk connection page. Select Add a receive scope, then choose All messages, Groups, or Direct messages. All messages includes every new message in accessible groups and new direct messages from all contacts. To receive all direct messages only, add Direct messages → All direct messages. Search appears after you choose Specific groups or Specific contacts. Return to the list to edit or remove a scope. For groups, choose Every new message or Only mentions. Direct messages trigger on each new message. Select Discard or go back to drop the edits in the scope editor. Select Save scope in the scope editor to return to the DingTalk scope list.

The default assistant requires confirmation before sending from a standard DingTalk connection.

To exclude a DingTalk group or contact, open a group or direct-message scope, and choose the Exclude selected scope rule. Search and check each group or contact you want to exclude. Uncheck an entry and save to resume intake. The collection cursor advances for messages filtered while the exclusion is active. If the device was offline or collection failed, previously unread messages may still arrive after intake resumes. Exclusions apply to new messages and dispatch of pending messages for this assistant, account, and source type.

Open Sidebar → My assistants → select an assistant you added → Assistant details → Manage assistant → Connections → DingTalk. After adding an individual group, open its scope to choose Mentions only (the default) or All messages. Existing individual groups can also be edited. Direct messages do not have this option. Click Save in settings to apply the change; cancel discards it. A scope change starts intake at its save boundary without importing earlier history. Receiving all messages does not mean replying to every message: responsibilities, handling settings and sending approvals still determine the response.

DingTalk groups set to All messages catch up in windows of up to 15 minutes. After a timeout, collection retries from the same starting point with a five-minute window. If that also times out, collection skips backlog older than five minutes and uses one-minute windows for recent messages. If timeouts continue, collection keeps advancing as time passes. Skipped messages remain available in DingTalk.

To investigate a missing group message, search the execution device’s dsh-core-runtime.log for wework-dingtalk-collection using the group ID and send time. The log records each polling window, the message IDs returned by the API, and connector filter reasons. Search executor.log for DingTalk group intake and the message ID to check subscription filter reasons or queue status. A pending status means the event entered the queue. These diagnostic entries contain only the metadata needed for troubleshooting.

You can manually mention yourself in a connected group to delegate work. You can also select yourself explicitly as a direct-message contact under filtered sources and save, then manually send instructions in your self-chat. The source's handling and approval policies still apply. Selecting all contacts alone does not enable this entry, and your outgoing messages to other contacts are not treated as instructions. Stand-in replies always retain DingTalk's AI-send marker.

For work requested in your DingTalk self-chat, the stand-in asks task-scope or missing-information questions in that same chat; subsequent answers follow the source's conversation policy. For messages from other people, missing information that the sender must provide is requested in the original DingTalk conversation. Decisions, choices or commitments that require you remain in Wework's Needs your input surface and the original work, without sending private owner questions to the other person. Business answers do not replace sending approvals or account authorization. Failed or uncertain clarification sends are reported with their actual state in Wework.

DingTalk source intake ignores messages explicitly identified as robot-sent or carrying an AI-send marker, regardless of sender. This prevents task notifications from the Wegent chat bot from triggering the stand-in again and creating a loop. Business messages from other bots do not trigger automatic handling either. Human-forwarded notifications and human questions quoting notifications remain actionable; conversation history reads still retain these notifications for context.

Each DingTalk message received automatically or read from history carries its original send time. The stand-in interprets “today” and “tomorrow” using the message's send date, then uses the execution device's clock at the start of the turn to check whether a deadline is approaching or has passed. If missing time or timezone information affects that judgment, the stand-in explains the uncertainty.

Choose manual delegation, approval before operations, or automatic handling independently for each source. New DingTalk sources default to approval before operations. The selected execution device uses its installed DingTalk plugin and account. Complete any requested authentication through the existing connector flow.

Screenshots in a connected conversation are downloaded through its read-only source query into host-generated temporary files, without another operation approval for viewing images. Missing account authentication or revoked source access still requires restoring that connection. To mention a colleague in a group, the stand-in must obtain their real person ID and pass the reply tool's mention parameter; typing “@Name” in the body produces text only. Reply sending still follows the source's confirmation settings, and message acceptance does not prove that the recipient received a mention notification.

Open My assistants → Assistant details → Manage assistant → Connections → source details → Processing. The Processing entry shows the current policy summary. Select Configure anywhere on the row to reveal its settings, or Collapse to hide them. Save the stand-in settings to apply changes:

  • Processing: Use the menu to choose Handle manually, Queue in background, or Handle on trigger. Background handling waits five minutes from the first pending event of the same source, then evaluates what needs action. New connections for the default assistant start in background mode. Connections for other assistants default to handling on trigger.
  • Start a new conversation each time: off by default, continuing the same conversation for this source. Turn it on to give each new event its own conversation. Reuse remains restricted to the same role, account and concrete source. Different groups, contacts and sources stay separate, including concrete sources inside an all-resources scope. Explicit replies return to their original work while it remains unarchived; redelivery never creates another conversation.

Processing and conversation settings are independent. Settings changes do not reorganize existing work or messages. New events can guide the active Codex turn in a reused source conversation. An active turn awaiting native approval can still receive messages while the approval stays pending. If there is no active turn to receive them, events wait for approval. Events requiring a stricter approval policy start a later turn. After a source conversation is archived, new messages (including replies quoting old messages) start a new conversation, which subsequent messages reuse. Old tasks and messages stay archived; redelivered old messages do not create conversations or execute again. To view or restore an old task, use Recent activity → View all activity → the work → Unarchive; restoration itself does not start a turn. Automatic dispatch includes only the selected messages, not previously ignored or deferred input. Project Issues keep independent conversations; scheduled work retains each arrangement's existing conversation mode.

Direct handling does not require responsibilities or preferences to be filled in. When exactly one role is eligible, an earlier background-coordinator failure or pending question does not block direct dispatch. Existing questions and failures remain visible; this does not automatically answer approvals or replay commands with uncertain outcomes. Coordinator retries recover from actual native sessions and execution receipts, not merely the existence of a task record.

Routine progress and successful role-task completion leave background coordination idle. Failures, cancellations, pending questions or approvals, and scheduled follow-ups can still trigger coordination. The coordinator runs silently and shares important findings through the assistant conversation.

Collaboration sources retain project membership permissions. Project-scoped agents cannot broaden intake to other projects or DingTalk sources. When roles overlap, AI selects one handler to avoid duplicate execution.

Background processing handles failures per event. If a cloud Issue cannot be read, its event is canceled or left pending for retry as appropriate. Other authorized source events continue to dispatch.

Connected collaboration projects display their names, including accessible projects whose parent workspace you have not joined. Names remain visible and existing connections can be removed when switching the stand-in execution device. New local project connections can only be added when executing on the current device.

Remote execution devices can still use the all-project scope. It uses the selected Executor's own project catalog; unconnected local projects on the editing computer are not shown as remote connections.

Work associations and approvals​

Choose execution by task needs: simple or tightly coupled work can run directly in the default assistant; internal decomposition can use permitted native subagents; separate work threads are for independent conversations, workspaces or durable tracking. Future-condition requests such as notifying the user about a new release use native schedules/monitors, not one-time threads or permanently running subagents. An arrangement takes effect only after its existing confirmation and a successful save. Execution choice does not change source grants, authentication or operation confirmations.

New events follow the source's conversation strategy; models no longer merge them automatically based on text similarity. Explicit replies retain their original conversation. Expand related messages in the preview to split a message into separate work or move it to another item within the same role. Moving a completed message does not execute it again.

Operation approvals appear in Needs your input and link to the original conversation's approval card. Use its approval or rejection action; no typed “yes” is required. DingTalk reply approvals show the outgoing text bound to the original tool call. Approval-before-operations uses runtime enforcement for file writes, commands requiring elevated permissions, and MCP tools with write annotations. Approval applies to the individual operation, without persistent allow rules. This policy currently requires the Codex runtime.

Shared human decisions​

Structured questions from stand-ins and ordinary tasks share one pending request. While the app is in the foreground, a compact reminder appears in the upper right; expand it to answer simple questions. The title-bar bell's Needs your input entry opens the shared tab to view and handle the original task or Issue in its own interface. Work lists and notification entries no longer contain independent reply forms.

The detail header shows the selected notification’s original question and entity name, keeping the question readable when narrow windows hide the list. Needs your input hosts the original entity: tasks navigate to the selected question's original conversation turn and show its native input card. Issues use the native execution and message IDs to focus the AI message that raised the question and its context, rather than the thread's initial comment. Opening a notification preserves the reading position; clicking Reply focuses the composer. Context, questions, forms, approvals, and authorization use the original interface and handlers. The inbox does not extract or summarize conversation content or create another reply form.

The container header's Open in original view action opens the owning task or Issue and preserves the source comment target. Files, reviews, plans, and execution details that require the full workspace open in the original task. Child Issues open their own detail page rather than adding workspace sidebars inside the inbox.

Opening an original task restores its title, model, and workspace so you can continue the conversation, even when the task is absent from the sidebar. Opening it preserves the sidebar's existing visibility rules.

Background delivery follows the notification channel settings. Eligible simple asynchronous questions support text replies through system notifications. Manage channels in the title-bar bell's settings; the account area no longer has a separate global IM notification menu. System delivery also depends on operating-system permissions and notification settings.

Reading a notification, dismissing a reminder, or marking it read does not resolve a request. Accepted replies or an already resolved original question move it into history; failed sends retain the draft. Offline devices retain last-known questions and drafts, with replies enabled only after reconnecting and revalidating. Execution approvals, connector login, and complex forms remain in their original context; ordinary business answers never grant operation permissions. Issue answers persist in the owning comment thread before continuing its execution.

Use Stop stand-in at the bottom left of settings and confirm to stop. Source and startup failures remain visible for retry after fixing authentication, model selection, or connection settings. Message cursors, deduplication records, and associations persist across executor restarts.

Source collection failures never permanently stop intake or require saving the connection again. The Executor retains the error and original cursor, then tries again on the next polling cycle; timeouts or transport failures with an explicit backoff resume after that delay. Sources previously stopped by database locks, configuration changes, invalid responses, or other collection errors also resume. Every attempt still checks the current account and permissions: unresolved authentication, permission, or response errors remain visible and never grant unauthorized reads. Success clears the error and advances the cursor, while existing message records prevent duplicates. Automatic recovery applies only to collection, never replaying sends or other actions.

Issue human handoffs​

Issue cards right-align an icon and the actor's name in the existing reference/status row above the title, without adding a row. Icons distinguish agent handling, stand-in handling and waiting for a person. Waiting uses a person with a small clock and a “Waiting for [person]” tooltip; only the name is visible as text. Confirmed running executions show the agent or stand-in, while outstanding questions prioritize their recipients. Otherwise the assigned person handles the Issue; when no person is assigned, its creator takes responsibility. There is no third handling state such as awaiting assignment. Business states remain independent, and execution details retain queued, failed and offline progress.

A structured asynchronous question raised in an Issue-bound execution is persisted on the Issue with its original thread, execution identity and handling record. The responsible participant or collaboration-group leader assigns a specific person. Until a recipient is selected, the responsible person handles the question, with the Issue creator taking responsibility when no person is assigned. There is no broadcast or default coordinator. AI reads list_human_requests; the reporting execution can explicitly flag dependent steps through set_human_request_blocking. This operation never transfers the question, resets its waiting time or grants assignment permission. The responsible participant uses assign_human_request to select the recipient.

Recipients answer through the shared Needs your input surface and the original Issue's question card. Targeted notifications reuse collaboration channel preferences. Answers persist in the owning comment thread and continue the original execution without granting access to another person's private Runtime or credentials. Reading does not resolve a request. Queued answers remain awaiting acceptance; only the owning execution's acceptance clears that question. Questions settle independently, and any unresolved question keeps the Issue on the human side. AI waits only for dependent steps while continuing independent work.

Cloud question reports and source blocking updates require a verifiable original execution record matching the project, Issue, Runtime task, device and execution owner. Manual task bindings alone, or group activities without matching canonical evidence, return a conflict (409). A same-named device or inferred owner cannot substitute for that proof; restore the original execution's trusted record first. Local projects retain their owning Executor's native source checks.

Saved board views support Only issues needing my input, evaluated for the current viewer rather than the view's author. Offline questions and drafts remain visible but require reconnection and authorization checks before replying. Native execution approvals and connector authentication remain separate from business answers.

The project toolbar also offers a one-click Needs my action filter without rewriting saved views. The global pending-work page includes native project work currently assigned to the viewer and explicit project questions, without duplicating the same question as ordinary work. Selecting project work opens the real Issue in the existing split view, without fabricating a Runtime task.

Waiting time and workflow analysis​

With you for starts at the current handoff and resets when another person takes over. Editing a question or blocking note, reading a notification, or saving an answer does not reset it. Ordinary work uses a reliable human assignment, initial creator handoff, or the current AI execution's completion. Historical records without current-turn evidence say Handoff time not recorded; update timestamps are not substituted. Timestamps are UTC and durations are elapsed wall time, not business hours.

Questions retain business events for requests, assignments, answers, delivery rejection and execution acceptance, including time, authenticated principal, recipient changes and original message identity, without copying answer bodies. These can support later analysis of waiting distributions, handoffs and successful continuation. A principal does not prove the physical operator was a human; waiting time, forwarding counts and reply length alone do not establish individual performance. Analysis must preserve project permissions and distinguish approval responsibilities, external dependencies, AI execution, non-working time and missing evidence. These are traceable business records, not a tamper-proof HR audit system. This feature does not automatically label people as bottlenecks or unproductive.

Issue assignment reception receipts​

Collaboration notifications read Stand-in history from the local Executor and online execution devices that support remote queries. A lookup failure identifies the device and reason; it means history could not be loaded, rather than an Issue execution failure. For incompatible versions, update that device's Executor and refresh notifications. Other desktop App devices are excluded from remote queries; local history still uses the native Executor.

Next to the assignee dropdown control, an outlined person with a check marks Read by recipient and a filled person with a check marks Received by stand-in. Hover to view the status and timestamp. While details refresh for the same Issue and assignee, the header retains displayed receipts without interrupting their hover tooltip. Changing the Issue or assignee hides receipts from the previous scope. A successful detail open records the human receipt; a stand-in records reception once its task is accepted, before execution completes. Both receipts retain their own timestamps and do not complete the Issue. Notification previews, marking all notifications as read, and background reads do not record a human receipt.

Assigners and recipients can view the receipts, which refresh while details remain open. The latest active assignment in the activity timeline shows the same receipts and updates together with the assignee control, without polling historical entries separately. Reassignment moves the displayed receipts to the latest assignment activity; unassignment removes the former recipient's receipts. Reassignment starts a new receipt history. Older assignments without reliable evidence show “No receipt recorded.” Executors retain pending cloud receipts for up to 30 days, increasing failed retry intervals to at most one hour. Restarting preserves the retry delay. Local-project receipts stay on the owning Executor.

Refreshing an Issue's status or other properties preserves receipt icons and pending hover tooltips for the same assignment. Reassignment, including assigning the same person again, immediately hides old receipts until the new assignment's results arrive.

Stand-ins save the recipient-owned device task binding and reception receipt before starting execution. Background handling records reception when the assignment enters its pending queue. Reception does not imply successful execution, and a later launch failure does not revoke it. Cloud acknowledgements still validate the active assignment, owned device and task binding; rejection diagnostics do not relax these checks.

Cloud assignment dispatch intents persist on their owning Executor. Transient cloud request failures recover with backoff, including after restart. A binding without a local task resumes the same task without depending on a successful binding deletion. Recovery revalidates the backend, account, current assignment, role and device; reassigned or disconnected project work is not replayed. Locally accepted tasks are not executed again by startup reconciliation. Model failures still use the original task's retry action, and configuration errors require human correction.

The desktop retries failed notification delivery with backoff until the Executor accepts it. When a restarted Executor reports missing cloud configuration, the desktop reapplies the current signed-in connection and connector authorization. Ordinary network disconnects remain owned by the Executor's existing reconnect loop.

To amend an existing arrangement in chat, the stand-in first reads the saved arrangement, then updates its content, name, trigger, time zone or enabled state in place. It should read available instructions and configuration instead of repeatedly asking you for those facts. Missing business choices require a question card; automatic execution must not be scheduled while they remain unresolved. Asking to use an existing automatic workflow does not prove that the workflow has been inspected, and postponing that investigation until the trigger time does not make the work ready.

“Read-only investigation” describes the preparation task's required behavior, not a new sandbox or tool-permission mode. It does not guarantee that preparation tasks are technically unable to write. Preparation retains the existing permission contract, network access, and tool approval rules; this change constrains scheduling decisions without expanding or restricting existing permissions.

The scheduled instructions should preserve your requested outcome and include the verified execution plan, without silently changing execution into a reminder. An explicit reminder needs its content and time, not an investigation of the underlying execution workflow. Successful creation means the arrangement was saved; it does not guarantee completion by the requested time or pre-approve external actions such as publishing. Execution still follows native permissions, approvals, and prerequisite checks.

Scheduled in the Tasks sidebar remains independent and retains its goal, target task, model, and execution environment settings without requiring experimental features. Scheduled tasks and Calendar connections manage separate lists, editors, and run histories. The stand-in work list contains concrete work.

The project conversation uses the existing collaboration group leader. Its header identifies the group and leader, and settings use the existing group configuration. Automatic project event handling enables that leader on the selected device. Each project/group has exactly one active member/device binding, with explicit takeover required for switching. Private chat and memory remain private until selected content is explicitly published to an Issue.
