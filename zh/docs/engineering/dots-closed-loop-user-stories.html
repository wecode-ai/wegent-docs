dots 启发的 Wework 闭环用户用例

目标与依据​

用真实隔离的 Wework Electron、执行器、任务存储和本地文件验证三个业务闭环：反馈变成经过测试的修复、范围变化变成一致的发布材料、新证据变成分析和具体行动。闭环必须包含来源、执行、检查、反馈以及可复查的交付物，不能以助手输出“完成”作为成功证据。

来源均在 2026-11-07 阅读：OpenAI 发布文章明确列出反馈修复、发布材料更新和研究分析更新；官方使用指南说明上下文、持续反馈及人工决策；MacRumors 行业报道关注持续工作和权限；9to5Google 行业报道介绍问题调查及人工审核。以下具体业务数据与验收步骤是 Wework 测试设计，不是上述文章中的事实，也不表示 Wework 兼容 dots 的所有能力。

环境、边界和证据​

  • 使用 pnpm --filter wework ai:verify start 启动隔离桌面会话；使用现有模型、独立工作区和个人主分身。不得操作个人 Wework 窗口或读取认证内容。
  • 用户明确选择本机 Codex 账号时，使用 WEWORK_E2E_NATIVE_CODEX_HOME="$HOME/.codex" pnpm --filter wework ai:verify start，让现有原生账号机制接入该账号；其余会话数据仍隔离。默认不继承账号，因此初始没有模型不代表模型目录缺陷。不得读取、打印或提交认证内容，完成后执行 ai:verify stop 清理会话链接。
  • 探索性实测使用真实模型；自动 E2E 可脚本化模型响应，但保留真实执行器、工具、文件、计算、任务委派、人工输入、持久化和交付物声明。
  • 主分身负责接收目标、委派任务和回传结果；子任务负责实际执行。每次结果都需核对实际文件或命令输出，并从主会话打开交付物。
  • 等待和运行期间至少离开再返回一次；完成后重新加载，检查结果、人工决定和当前版本是否保留。状态、错误、焦点、等待提示、重复回执和导航问题均记入实测记录。
  • 只使用测试拥有的本地 Git 仓库和文件。业务用例中不发送外部消息、不发布公告、不推送远程仓库。
  • 自动 E2E 在已有私有 Git 基线上创建真实 linked worktree，将其中 stories/ 子目录作为所选当前工作区，保持 current_workspace 执行模式。主分身和子任务摘要必须保留该精确路径及 workspace 类型，不能因祖先目录属于 Git worktree 就冒充托管 worktree；不覆盖 Shell 的 workdir，独立检查原生默认 cwd，并在重载后单击主会话的真实交付物卡片验收文件预览。
  • 清理时停止活动子任务和隔离会话，恢复测试配置，清理测试数据。截图、日志、会话文件和本地调查证据不提交。

用例一：客户反馈到经过验证的软件修复​

用户故事： 作为产品工程师，我希望主分身调查客户反馈并委派修复，返回经过测试的变更，以便直接审查可工作的修复。

前置与数据： 创建独立 cart-fixture/ Git 仓库，包含 cart.mjs、cart.test.mjs 和 feedback.md。故障函数 totalCents(items) 忽略数量。反馈样例为单价 1200 分、数量 2，加单价 500 分、数量 1；故障结果 1700，正确结果 2900。使用 Node 内置测试，无外部安装。

步骤与验收：

  1. 在主分身提交反馈和目标，要求委派任务、复现、添加回归、修复及本地交付，限制只改测试仓库。
  2. 打开子任务，确认新增数量回归先失败，再因实际函数修复而通过；失败输出应包含 1700 与 2900 的差异。
  3. 返回主会话，核对真实测试结果和变更路径；通过应用查看代码或差异，独立运行 node --test cart.test.mjs。
  4. 追加反馈：数量为零时金额为零。继续原工作，补充有效测试并确认前次修复仍通过。
  5. 重新加载，确认最新结果与可审查的变更仍可找到；每次完成只返回一次相应业务结果。

异常与恢复： 复现时失败是必要证据，不能被当作最终成功。真实运行失败或模型不可用时应显示错误并通过产品入口恢复；不能重复运行未修复的测试来获取偶然通过。验收需证明空列表、正常数量和零数量都正确，且测试仓库外无变更。

用例二：发布范围变更到人工确认后的发布材料​

用户故事： 作为发布负责人，我希望分身核对范围变化、提出需要我的决定，再同步修订所有发布材料，以便批准一致的客户承诺。

前置与数据： scope-v1.md 包含 CSV 导出、自动定时、2026-11-20 全量发布；scope-v2.md 只保留 CSV 导出、自动定时延期、仅 beta 用户，但缺少日期。现有 announcement.md 和 launch-checklist.md 仍是旧承诺。

步骤与验收：

  1. 主会话要求委派核对新旧范围，在日期确认前保留现有材料，准备变更方案。
  2. 子任务提出结构化问题：“保留 11 月 20 日 beta”或“延期到 11 月 27 日 beta”，说明影响。未答复时应明确等待，不能擅自编造日期。
  3. 离开再返回后回答测试决定：“保留 11 月 20 日，仅 beta 用户”。此答案不授权外部发布。
  4. 确认原工作继续，实际生成一致的公告、检查表及 scope-change-summary.md：CSV 导出、beta、11 月 20 日；自动定时明确延期。
  5. 追加修订：“公告明确写出本次 beta 不含自动定时”。审阅实际内容，并重新加载验证最终版本可找回。

异常与恢复： 无答案或取消不能自行选择；缺失来源不能猜测。真实回答必须驱动同一工作的后续执行，不产生重复子任务。不允许把草稿描述成已发送或已发布。

用例三：新商业数据到修订分析和决策落实​

用户故事： 作为销售运营负责人，我希望分身根据订单变化刷新分析、解释影响，并落实我选择的跟进优先级，避免按过期数据行动。

前置与数据： CSV 字段为 order_id,customer,amount_cents,status。初版为 O1/Aster/10000/paid、O2/Birch/20000/paid、O3/Aster/5000/pending；保存不可变初版。新版将 O2 改为 refunded，并增加 O4/Cedar/30000/pending。

步骤与验收：

  1. 主会话委派读取 CSV，产出可重复运行的分析脚本和报告，确认初版已付 30000 分、待付 5000 分。
  2. 测试操作员更新真实 CSV 为新版，在原会话要求继续刷新；确认实际重新读取，而非复述旧结果。
  3. 独立运行脚本：新版已付 10000、退款 20000、待付 35000，总额 65000 分；已付减少 20000 分，相对初版下降约 66.67%。退款不能仍计入已付。
  4. 通过结构化问题选择“优先跟进 Cedar 待付款 30000 分”或“先调查 Birch 退款 20000 分”；回答前应等待。
  5. 回答“优先 Cedar，只准备内部清单”，确认实际写入 followup-plan.md，明确 O4、金额、优先级和待审核边界。主会话可打开最终报告与跟进计划。
  6. 重新加载验证新版结果与决定保留，旧版回执不能覆盖新版完成状态。

异常与恢复： 将金额改为 not-a-number 应显式校验失败，不能当作零或仍声称成功。恢复有效数据后继续原工作，核对数值恢复正确。不得暗示已联系客户。

自动化集成和结果记录​

复用 wework/e2e/desktop/ 的共享 runner、checkpoint、模型协议、委派结果与交付物预览逻辑。已有会议、周报、来源版本和邮件闭环仍需保留；这些测试不能替代本页的真实变更、计算和人工决策断言。新增 checkpoint 必须自建最小前置并进入现有 GitHub CI，不增加独立测试服务或重复构建。

每条实测记录应包含环境、输入、任务标识、步骤实际结果、命令退出码、文件内容、失败根因、修复、独立复审和重验结果。正式合并说明需区分真实模型探索、仅模型脚本化的 E2E 和尚未验证的外部服务能力。本页定义验收方案；运行是否通过以相应执行证据及 PR 检查为准，不预填通过结果。
