桌面升级、回退与 E2E 维护

升级的目标是缩短关闭应用到重新可用之间的时间。下载、解压、组件组合及插件运行目录准备均在当前应用仍可用时完成；只有目标环境准备完整，才提示重启。主程序和匹配组件作为一个完整版本切换，用户数据独立保存。

清单兼容和升级路径​

继续使用既有 Electron YAML 和 components-<channel>-<platform>-<arch>.json，不更换发现地址、不改变原字段含义。组件清单新增 upgradePolicy，其中每个目标版本声明 minSourceVersion，并记录明确的来源版本、目标版本、交付包哈希及升级和回退 E2E 证据。

旧客户端忽略新字段，继续直升旧清单中声明的最新版。路径约束从客户端包含新实现开始生效；不将改造前的旧版本纳入新 E2E 矩阵，也不把旧渠道固定到桥接版。

minSourceVersion 是约束，不是兼容证明。即使 A 高于最低版本，没有通过验证的 A → B 边也不能升级。客户端选择通往所选渠道最新可达版本的最短路径，每一跳单独确认。测试中的 B 只需比 A 新，不要求 B 是全局最新版。

撤销版本或升级边会阻止新安装；已下载的更新也会在切换前重新检查。没有路径时显示明确原因，不退回不受约束的直升逻辑。

准备、切换与恢复​

  • releases/slots/<id> 保存完整主程序、运行时缓存和准备好的插件 profile。目标包自己的准备入口执行准备工作，不使用旧版代码推测新版要求。
  • active 是启动器选择的版本指针；激活日志记录来源、目标、快照与试运行标识。原生启动器不加载目标版本业务代码。
  • 确认更新后先停止所有数据写入者，再保存迁移数据快照，随后退出并切换。后台复制运行中的数据库不能替代一致性快照。
  • 停止 Executor 或 app-server 时保留活跃 Goal 的恢复日志。上一回合已完成不代表 Goal 已完成；退出通知或通知流关闭不能用旧回合结果提前结束 Goal。
  • 运行时和主界面都就绪后确认健康。试运行退出或 60 秒未就绪，启动器进入恢复流程，不循环自动重启。
  • 已确认的手动回退独立记录事务方向；恢复中断后继续完成回退，不使用目标版本上一次的健康标记取消回退。
  • 旧版可以读取现有数据时直接切回；目标打开数据后发生不兼容失败，则先询问是否恢复快照。恢复前保留更新后的数据。目标在打开数据之前退出，可直接回退。
  • 快照注册表只包含迁移拥有的存储，包括任务 SQLite 及其 WAL/SHM、桌面偏好、持久化 renderer storage 和会话同步状态。新增迁移存储时必须同步更新注册表与恢复测试。源码仓库、云端记录及个人凭据不在恢复范围内。
  • 不兼容恢复还保留被回退版本的完整槽位，避免后续清理删除新版用户插件数据。preserved-data/<snapshot>/retained-release 记录对应槽位；保留的数据不自动过期。
  • 插件配置在准备期间变化会使准备结果失效；切换前再次核对，禁止重启后再补做大规模准备。

三层测试，分别维护​

层级数据来源验证内容能否开放正式升级边
策略与事务测试小型清单和临时文件目录最低来源版本、路径、撤销、激活日志、快照恢复边界否
机制回归 E2E从源码分别打包、签名的固定 A/B 夹具真下载、真解压、真 Electron/Executor、切换、恢复、任务继续执行否
发布版本对 E2E不可变的实际来源包和本次交付目标包指定版本对的完整升级与回退是，且仅限该平台、架构和包哈希

场景集中在 app-upgrade.scenario.mjs，套件版本和场景列表集中在 upgrade-suite.mjs。四个 checkpoint 分别检查正常升级、包含升级的手动回退、已确认回退被中断后的恢复及目标进程启动失败后的恢复；每个 checkpoint 建立自己的最小数据，不能依赖上一个场景。

套件 v5 分别限制整包准备、解压和运行环境准备阶段，每阶段最多 5 分钟；阶段必须单向前进，停滞或失败立即终止，不能把单个步骤的预算误作所有串行操作的总预算。目标包将 profile 复制、组件准备、运行环境物化及 profile 准备的开始、结束和耗时写入 logs/release-preparation.log，CI 必须保留该日志。

夹具由共享 runner 准备一次，所有场景复用。仅执行升级场景时直接复用 A 包，不额外构建不会启动的通用桌面包。版本号是输入数据，不决定断言分支。只允许模型服务替身；发布文件由真实 HTTP 服务提供，下载、签名、解压、存储、原生启动器及 Executor 都执行实际实现。故障场景终止真实目标进程，不伪造“回退成功”。

每个场景先通过来源包自己的无界面准备入口建立“已安装客户端”的运行环境，再开始 UI 操作；不重复把冷安装当作升级步骤。目标包仍须自行解压并准备独立版本槽位。升级和回退后逐项核对 host、Core、插件、executor、Codex 和 DWS 的实际路径与该槽位的准备结果，禁止继承来源包的固定路径覆盖。回归夹具写入独立输出目录，不覆盖正式包或同一 runner 中其他 checkpoint 的应用。

固定回归夹具使用不同版本和数据兼容声明，覆盖需要恢复快照的路径。它们从源码独立构建，不重命名现有 ZIP，也不修改已经签名的包来伪造版本。产物标记为 regression，发布门禁拒绝将它们提升成正式边。

日常修改与执行​

node --test wework/scripts/upgrade-policy.test.mjs wework/scripts/upgrade-evidence.test.mjs
pnpm --dir wework/electron test src/runtime/release-store.test.ts src/runtime/release-snapshot.test.ts src/runtime/release-profile.test.ts
pnpm --filter wework e2e:desktop -- --parallel-segments upgrade-and-rollback

runner 自动构建当前源码所需的独立 A/B 包。已有版本对时，通过 WEWORK_E2E_UPGRADE_PAIR、WEWORK_E2E_APP_BIN 和 WEWORK_E2E_EXECUTOR_BIN 指定；设置 WEWORK_E2E_REQUIRE_RELEASE_PACKAGE=1 保留包身份和签名，不能重签实际发布包。

维护规则：

  1. 改行为时修改共用场景；发新版本时修改版本对配置，不复制测试代码，也不把历史用例自动改指向最新版。
  2. 接受标准有实质变化时增加套件版本，使旧证据不能为新边背书。
  3. 每次失败保留完整日志，定位并修复后再运行；不以重试、跳过或削弱断言获取通过。
  4. macOS arm64、macOS x64 和 Windows x64 分别运行。同一套场景不能以另一个系统的通过结果替代。
  5. 截图、测试包、快照、会话目录和临时恢复数据均不提交仓库，CI 仅上传经过筛选的诊断与结果文件。

Wework Upgrade E2E 在非草稿 PR 的 ci:all 中对三个平台执行完整场景，也支持手动触发。接受标准版本统一由 upgrade-suite.mjs 管理；增强断言后重新构建夹具，不能复用旧套件证据。

原有 app-update-full checkpoint 复用这套真实版本对场景，保留慢速整包传输、请求不阻塞、禁止 Range/blockmap 和重复准备复用的断言，并与四种升级/回退场景一起在各平台 CI 执行。它不再通过复制 ZIP、修改文件名和附加字节来伪装新版本。

升级边显式记录 fromSourceSha 和 toSourceSha，必须分别匹配交付包元数据中的 sourceSha；E2E 结果同时记录这两个提交号。缺失或不匹配的提交号不能晋升，客户端还会校验下载包内的提交号。诊断日志写入失败仅输出诊断错误，不阻止实际准备，也不能覆盖准备失败的原始原因。原生启动器在超时恢复数据前必须终止完整运行时进程树，包括独立进程组中的写入进程。

发布版本对​

wework/upgrade-policy.json 维护本次目标的最低来源版本和希望开放的 sourceVersions。首次支持新协议的版本可以没有入边；之后发布必须声明并验证至少一条入边。来源可固定在某个已发布版本，不要求每次选择紧邻版本。

发布作业为 macOS 和 Windows 生成完整便携版本包，从既有发布下载指定来源包，通过共享 checkpoint runner 运行升级和回退。成功结果绑定来源/目标版本、包哈希、平台、架构、套件版本和 CI run。只将验证成功的边合并进组件清单；旧边和其引用的中转包必须保留。修改已发布包内容会使哈希验证失败，必须作为新版本重新发布和验证。

来源包可以来自另一渠道，例如 Beta → Stable。必须用目标渠道的真实升级/回退结果建立新边；只引入已验证来源节点，不复制另一渠道的升级边。证据同时绑定渠道，同一版本的包哈希在两个渠道也必须一致。

在推广滚动清单前，先上传不可变目标包和证据。任何必需版本对失败都阻止推广。最低版本、源码兼容声明或单元测试通过都不能替代真实版本对证据。
